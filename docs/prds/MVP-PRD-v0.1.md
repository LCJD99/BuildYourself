# 长期目标进程管理 · MVP PRD v0.1

> 状态：内部对齐稿  
> 日期：2026-11-08  
> 目标：对齐产品方向、MVP 边界、核心流程与验收标准  
> 非目标：替代详细技术设计、UI 视觉稿或最终开发排期

---

## 1. 文档目的

本文档用于回答以下问题：

1. 我们到底在做什么产品，不做什么产品？
2. 用户如何用产品推进多个长期目标？
3. 知识图谱、规则引擎和 AI Agent 各自负责什么？
4. 首版必须交付哪些能力？
5. 哪些事情已经决定，哪些事情仍待技术和产品进一步评估？
6. 团队用什么端到端场景判断 MVP 是否成立？

本文档是 `MVP PRD v0.1`。它用于统一方向，不等同于可直接进入开发的最终需求规格。

---

## 2. 一句话产品定义

> 一款以个人执行知识图谱为核心的长期目标进程管理系统。用户通过目标相关待办推进计划，通过证据更新进度，通过历史日历进行复盘；规则与规划引擎负责稳定控制，单一上下文 AI Agent 负责理解输入、提出候选关系和解释建议。

产品不是课程平台，也不是完整日程表。

产品的核心问题是：

> 用户同时推进多个长期目标时，是否在正确的事情上持续投入？计划是否仍然合理？根据现实反馈，下一步应该保持、调整还是暂停？

## 3. 核心产品判断

### 3.1 产品边界

产品管理：

- 长期目标。
- 目标所属项目。
- 外部承诺与内部计划。
- 里程碑与关键成果。
- 执行证据。
- 跨目标、跨项目的依赖、冲突与协同。
- 基于现实变化的计划调整。
- 阶段性复盘。

产品不管理：

- 用户一天中的所有琐事。
- 完整日历和普通会议安排。
- 课程内容交付。
- 通用待办清单。
- 社交、排行榜和多人协作。
- 专业医疗诊断或替代专业教练。
- 一个不可解释的“人生完成率”。

### 3.2 三个不可动摇的原则

1. **知识图谱是权威状态。**  
   目标、承诺、活动、证据和关系以结构化数据为准，不以聊天记录为准。

2. **AI 不直接控制权威状态。**  
   AI 可以理解、抽取、提问、建议和解释，但写入必须经过 schema 校验、规则检查或用户确认。

3. **证据优先于完成动作。**  
   完成任务可以更新执行状态，但不自动代表能力或长期目标已经取得进展。

## 4. 目标用户与核心场景

### 4.1 首批目标用户

同时推进多个长期目标、已有明确行动意愿，但计划容易因新任务和资源冲突而失序的人。

典型特征：

- 有外部截止时间，例如课程作业、项目交付。
- 有长期能力目标，例如英语表达、健身。
- 同时有多个目标，但时间、精力或恢复资源有限。
- 已有碎片化工具，但缺少跨目标协调。
- 愿意提供最低限度的结果证据。

首版不按年龄或职业硬性限定，也不限制具体目标领域。学习、健身、项目型目标作为首批深度模板。

### 4.2 核心用户任务

- 当我收到新的课程作业或项目任务时，知道它会如何影响现有长期目标。
- 当我同时推进多个目标时，知道今天最值得推进什么。
- 当我完成很多活动但结果没有变化时，知道问题可能在哪里。
- 当我出现计划偏差时，得到一份可执行且可解释的调整。
- 当我回顾一段时间时，看见自己实际把时间投入到了哪里。
- 当我需要判断一个目标是否值得继续时，看到结果、执行和证据状态。

### 4.3 首批不作为重点的人群

- 只需要提醒事项或普通待办的轻度用户。
- 只想管理完整日程和会议的用户。
- 不愿提供任何执行或结果证据的用户。
- 需要医疗、康复、心理或营养诊断的用户。

## 5. 产品信息架构

产品采用三层 UI，不使用多个独立 Agent。

### 5.1 一级：目标组合总览

回答：我现在在追什么，哪些目标需要关注？

展示：

- 所有活跃目标的统一摘要。
- 当前状态。
- 下一里程碑。
- 最近证据。
- 风险提示。
- 今日关键推进项。
- 跨目标冲突或协同提示。

不在这里展示：

- 所有任务。
- 所有详细图表。
- 完整日程。

统一摘要保证不同目标即使使用不同图表，也能够在组合层比较。

### 5.2 二级：单目标工作区

回答：这个目标现在进展如何，下一步做什么？

固定信息结构：

1. 目标地图。
2. 当前进度视图。
3. 里程碑与承诺。
4. 近期证据。
5. 下一行动。
6. 复盘入口。

项目可以根据数据特点使用不同可视化，但操作顺序和信息结构保持一致。

### 5.3 三级：行动与证据详情

回答：这个任务、承诺、里程碑或关系具体是什么状态？

包含：

- 所属目标与项目。
- 截止时间。
- 预计耗时。
- 依赖和冲突。
- 完成标准。
- 证据要求。
- 最近变更。
- AI 建议。

优先使用侧边抽屉或详情弹层，保留用户当前的页面上下文。

### 5.4 导航要求

- 使用面包屑表达层级，例如“目标全景 / 英语课程 / 展示作业”。
- 从详情返回时恢复原来的筛选、滚动位置和选中节点。
- 用户可以从总览直接进入目标，但不需要被迫逐层点击。

### 5.5 Agent 位置

- 全产品只有一个 Agent。
- Agent 以页面边缘可展开助手的形式存在。
- 展开时明确显示当前上下文，例如“正在讨论：英语课程 / 展示作业”。
- 不同 UI 层级提供不同上下文，不创建多个割裂的聊天机器人。

## 6. 核心概念与知识图谱

### 6.1 双层知识图谱

#### A. 个人执行图谱

记录某个用户当前的真实状态，包括：

- 长期目标。
- 项目。
- 外部承诺。
- 内部任务。
- 里程碑。
- 能力。
- 约束。
- 证据。
- 干预与调整。
- 复盘。
- 不同对象之间的关系。

#### B. 领域知识图谱

记录受控的专业方法和判断依据，包括：

- 学习、健身和项目管理的通用方法。
- 目标类型和活动类型。
- 评价标准与证据要求。
- 已知约束、依赖和冲突类型。
- 外部来源、适用条件和版本。

领域知识图谱不是通用世界百科。它只覆盖产品实际支持判断的语义和方法。

运行时，个人执行图谱提供用户状态，领域知识图谱提供判断规则和合理解释。

### 6.2 核心实体

| 实体 | 定义 |
|---|---|
| Goal | 至少持续 4 周、可拆成里程碑、有成功描述的长期目标 |
| Project | 围绕目标组织的工作包，一个项目可以服务多个目标 |
| Commitment | 有责任方、范围或截止时间的外部或内部承诺 |
| Task | 可执行的行动单元，必须关联目标或项目 |
| Milestone | 可以验收的阶段性结果 |
| Capability | 需要长期提升的能力 |
| Evidence | 证明任务完成、能力变化或目标进展的材料和数据 |
| Constraint | 时间、精力、恢复、资源、外部规则等限制 |
| Intervention | 系统或用户采取的一次调整 |
| Review | 对一段时间内执行、结果和关系的复盘 |

### 6.3 核心关系

至少支持以下关系类型：

- `属于`：实体属于某个目标或项目。
- `依赖`：完成 A 需要先完成 B。
- `贡献`：活动或能力有助于某个目标。
- `衡量`：证据衡量任务、能力或里程碑。
- `约束`：某个条件限制计划或活动。
- `竞争`：多个对象争夺同一时间、精力或恢复资源。
- `协同`：多个对象可以共享投入或互相促进。
- `替代`：某个活动可以替代另一个活动完成相似贡献。
- `验证中`：AI 提出但尚未被用户或数据证实的关联。

### 6.4 关系可信状态

每条推断关系必须包含：

- 来源：用户确认、规则、专业资料、AI 推断。
- 置信状态：候选、已确认、已验证、已否定。
- 证据引用。
- 创建时间和版本。
- 最后更新时间。

AI 推断出的关系不能直接作为既定事实展示或用于高风险计划调整。

### 6.5 历史与版本

- 当前状态保存在知识图谱中。
- 状态变化保存在事件日志中。
- 评价标准、目标契约和重大计划调整必须版本化。
- 新的标准不能追溯重算旧进度。

## 7. 系统控制与 AI 权限

### 7.1 推荐运行链路

```text
用户输入 / 任务 / 反馈 / 可选日历容量
                    ↓
        LLM 提取候选对象与候选关系
                    ↓
 Schema 校验、实体对齐、必要澄清
                    ↓
              用户确认低可信变更
                    ↓
             写入个人执行知识图谱
                    ↓
       规则引擎计算进度、冲突和风险
                    ↓
         规划器生成一份推荐调整
                    ↓
         LLM 解释原因并呈现取舍
                    ↓
       用户确认 / 执行 → 记录证据
                    ↓
       图谱更新 → 周复盘 → 下一轮计划
```

### 7.2 唯一 Agent 的职责

- 理解自然语言输入。
- 提取目标、承诺、任务和证据候选。
- 向用户询问缺失信息。
- 提出候选关系。
- 将规则计算结果解释为可理解的语言。
- 提出一次具体调整。
- 记录用户确认、拒绝或修改的原因。

### 7.3 规则与规划引擎的职责

- 校验计划是否满足容量和硬约束。
- 计算交付、阶段、趋势和风险。
- 检测跨目标和跨项目冲突。
- 选择每日唯一推荐安排。
- 处理临时任务进入后的重排。
- 确保结果可重复、可测试。

### 7.4 自动化权限

Agent 可以自动：

- 生成内部草稿计划。
- 移动低优先级任务。
- 提出候选关系。
- 更新任务执行状态。
- 生成复盘草稿。

以下操作必须用户确认：

- 写入或修改外部日历。
- 改变目标、成功标准或评价标准。
- 取消外部硬承诺。
- 进行重大资源取舍。
- 确认高置信度的能力进展。
- 将候选关系升级为已确认关系。

## 8. 核心功能需求

### 8.1 目标管理

#### 规则

- 最多 10 个活跃目标。
- 暂停、完成和归档目标不计入活跃数量，不设数量上限。
- 达到上限后，用户需要暂停、归档或完成一个目标，才能增加新的活跃目标。
- 系统不因为技术限制而阻止创建 10 个以内的目标。
- 资源容量不足时，系统展示风险，不允许无提示地忽略。

#### 目标进入活跃状态的条件

至少具有：

- 成功描述。
- 至少一个可观察的结果、能力或交付证据。
- 一个复盘周期。

不满足时只能保存为草稿，不能进入自动规划和监督。

#### 生命周期

MVP 只定义最基础状态：

```text
草稿 → 活跃 → 暂停 / 完成 / 归档
```

- “有风险”是派生状态标识，不是生命周期状态。
- 完成需要系统证据条件满足后由用户确认。
- 暂停目标保留历史，但退出每日规划。
- 放弃或归档需要记录原因。

### 8.2 目标创建

采用“自然语言访谈 + 模板”的混合方式：

- 用户描述目标。
- Agent 提出目标结构、里程碑、约束、证据和候选关系。
- 用户确认或手动编辑。
- 通过 schema 校验后写入图谱。

首版提供学习、健身、项目型目标的深度模板。其他目标使用通用模型，不以“领域不匹配”阻止创建。

### 8.3 外部承诺输入

支持用户粘贴或输入教师通知、项目要求和临时任务。

系统应提取：

- 交付物。
- 截止时间。
- 子任务。
- 预计耗时。
- 依赖关系。
- 验收要求。
- 所属目标。

流程：

1. 生成候选承诺与任务。
2. 展示不确定字段。
3. 请求必要澄清。
4. 展示对当前目标和容量的影响。
5. 生成一份调整后的推荐计划。
6. 用户确认后写入。

不提供多套并行方案供用户比较。

### 8.4 每日规划

#### 默认节奏

- 周计划作为基线。
- 每天生成一份具体的今日待办。
- 日常打开页面不重新生成计划。

#### 重排触发条件

只有出现以下情况才重排：

- 新的硬承诺。
- 截止时间或范围发生变化。
- 可用时间或约束发生变化。
- 用户明确表示当前计划不可执行。
- 出现重大执行偏差。

#### 输出要求

- 只输出一份推荐安排。
- 不默认提供备选方案。
- 说明调整影响了什么、顺延了什么、为什么。
- 用户可以直接编辑计划，编辑记录进入事件日志。

#### 今日视图

展示目标相关待办：

- 优先级。
- 预计耗时。
- 建议时段。
- 所属目标。
- 关联里程碑。

不提供完整时间轴或拖拽式日历。

系统可以突出少量最影响目标的推进项，但不为数量设置产品硬上限。

### 8.5 任务规则

- 任务必须关联一个活跃目标或目标下的项目。
- 不提供独立的、与目标无关的通用待办收件箱。
- 用户可手动添加目标相关任务。
- 任务可以设置完成标准与证据要求。
- 任务完成与目标进展分开计算。

### 8.6 证据

支持四类证据等级：

| 等级 | 说明 | 默认可信度 |
|---|---|---|
| E0 | 不需要证据 | 仅执行状态 |
| E1 | 用户自报 | 低 |
| E2 | 可验证产出 | 中 |
| E3 | 外部专业反馈 | 高 |

要求：

- 任务和里程碑可以配置最低证据等级。
- 关键里程碑至少需要 E2 或 E3 才能形成高置信度进展。
- 用户自评可以记录主观体验和目标意义，但不能单独触发高置信度能力进展。
- 每条证据必须保存来源、时间和关联对象。

### 8.7 进度评价

评价不能只依赖教师评分。采用多源分层标准：

1. **目标契约**：最终要达成什么，是最高层定义。
2. **结果与能力指标**：项目类型决定需要看哪些表现。
3. **外部标准与专业反馈**：课程要求、教练反馈、考试或作品评审等，是重要证据。
4. **执行数据**：完成率、时长、负荷、频率，反映过程。
5. **现实应用与迁移**：真实展示、比赛、作品、工作场景中的表现，是最终验证。

默认评价重点：

- 交付型项目：里程碑、质量、验收。
- 学习型目标：掌握、留存、迁移和真实输出。
- 健身目标：表现、能力趋势、训练负荷与恢复。
- 通用目标：结果证据、用户自评和现实场景验证。

冲突时：

- 用户确认的目标契约为最高标准。
- 硬性外部要求作为约束。
- 外部反馈可以修正能力判断。
- 外部反馈不能未经确认改变长期目标。

### 8.8 模糊进度

允许使用近似进度，但必须满足：

- 反馈先进入证据层。
- 规则引擎依据项目标准计算进度区间。
- LLM 不独立决定进度百分比。
- 显示离散状态、区间或置信状态，而不是虚假的精确值。
- 图表旁边同时展示证据数量、来源和最后更新时间。

示例：

```text
口语表达：推进中 · 约 55%—65%
证据：2 份自评录音、1 次课程反馈
置信：中
```

### 8.9 不同项目使用不同可视化

首版固定支持六类视图：

1. 进度条：固定交付物和明确分母。
2. 阶段/里程碑图：能力成长和阶段性目标。
3. 趋势图：连续指标和结果变化。
4. 关系树/图谱：目标结构与跨项目关系。
5. 饼图/环形图：进度区间或资源/活动构成。
6. 历史日历热图：实际执行和证据分布。

#### 视图规则

- 项目类型提供默认视图。
- 用户可以在数据语义合法的视图之间切换。
- AI 可以推荐视图，不能任意发明图表类型。
- 数据不足时显示“证据不足”，不自动切换到“更好看”的替代图。
- 图表数据和计算由规则或查询引擎产生，结果必须可复现。

#### 环形图语义

环形图有两种互斥模式：

- 进度模式：进展区间 + 证据状态。
- 构成模式：时间、活动或资源分配。

同一张图不能同时混合“进度”和“构成”两种含义。

### 8.10 历史进度日历

用途：复盘实际发生了什么，不用于规划。

展示：

- 每个日期涉及的活跃目标。
- 完成的目标相关活动。
- 是否存在证据。
- 可选按目标筛选。
- 点击日期查看当天证据和复盘摘要。

规则：

- 只读。
- 不能在日历上创建、拖拽或规划任务。
- 不显示与目标无关的事项。
- 外部日历只作为容量约束，不进入历史进度日历。

### 8.11 跨目标关系

支持的关系必须能够转化为行动或判断，不做无意义的连线展示。

重点关系：

- 时间冲突。
- 精力冲突。
- 恢复冲突。
- 前置依赖。
- 能力贡献。
- 共享材料或活动。
- 资源替代。

每周最多在首页呈现少量与当前决策有关的跨目标提示，其他关系放在目标工作区和复盘中。

### 8.12 周复盘

周复盘回答：

1. 哪些目标真正取得进展？
2. 哪些目标只是执行很忙？
3. 偏差来自计划、方法、精力、外部事件还是证据不足？
4. 下周只调整哪个最关键变量？

输出：

- 事实。
- 待验证推断。
- 一个具体调整建议。
- 预期结果。
- 验证时间。
- 用户确认或修改记录。

### 8.13 可选外部日历

- 用户可以自行选择是否导入现有日历。
- 导入用途仅限判断可用时间和容量约束。
- 外部日程默认不在产品界面展示。
- 外部日程不进入目标统计、历史进度日历或最终交付物。
- 需要把计划写入外部日历时，必须由用户确认。

## 9. 端到端主场景

### 9.1 场景：教师新增作业触发计划调整

前提：

- 用户有“英语表达”“健身”“项目交付”三个活跃目标。
- 本周原计划容量充足。

事件：

> 英语老师新增展示作业，周三前提交大纲，周五前完成 3 分钟口语录音。

期望过程：

1. 用户粘贴教师通知。
2. Agent 提取交付物、截止时间、预计耗时和所属英语目标。
3. 系统显示待确认字段。
4. 用户确认。
5. 图谱新增承诺和子任务。
6. 规则引擎计算新增容量与冲突。
7. 规划器生成一份调整后的计划。
8. 系统说明哪些活动被顺延以及原因。
9. 用户确认计划。
10. 今日待办与原计划相比只发生必要变化。

期望结果：

- 不提供多套组合方案。
- 不取消长期目标。
- 不未经确认删除外部硬承诺。
- 不因为刷新页面产生新的计划结果。

### 9.2 场景：完成任务但没有满足证据

1. 用户完成一次口语任务。
2. 任务执行状态变为完成。
3. 系统记录“口语输出 2 分钟”。
4. 由于目标是 8 分钟表达，且没有达到里程碑证据规则，能力进度不自动提升。
5. 页面显示：执行已完成，能力证据仍不足。

### 9.3 场景：证据满足阶段门槛

1. 用户提交录音和课程反馈。
2. 证据等级达到里程碑要求。
3. 系统计算新的进度区间。
4. 当前可视化更新。
5. 历史日历显示当天英语活动与证据。
6. 周复盘引用新证据，不重新解释旧结论。

### 9.4 场景：跨目标资源冲突

1. 新项目任务与高强度训练占用同一时间。
2. 规则识别冲突。
3. 目标组合层展示冲突对象和影响。
4. 系统优先保护硬截止时间和恢复约束。
5. 生成一份调整结果。
6. 如果仍无法满足，要求用户确认牺牲或延期哪个目标。

## 10. MVP 范围

### 10.1 MVP 必须包含

- 目标创建与目标契约。
- 最多 10 个活跃目标的目标组合总览。
- 三层式目标工作区。
- 个人执行图谱与受控领域知识图谱。
- 目标、承诺、任务、里程碑、证据和关系管理。
- 教师通知或任务文本解析。
- 每日目标相关待办。
- 单一推荐计划与临时任务触发的重排。
- 证据等级与多源评价。
- 差异化进度视图。
- 只读历史进度日历。
- 跨目标冲突与协同提示。
- 周复盘与一次调整建议。
- 单一上下文 Agent。

### 10.2 明确不在 MVP

- 课程内容生成和课程市场。
- AI 教学产品定位。
- 完整日程规划和拖拽日历。
- 与目标无关的通用待办。
- 多人协作、教练账号和社交。
- 任意图表生成器。
- 自动医疗、康复、营养或心理诊断。
- 自动修改目标标准的 Agent。
- 只依赖向量检索或聊天记忆维护系统状态。

### 10.3 未决事项

以下事项暂不阻塞产品方向对齐，由后续产品、技术和合规评估：

- Web、PWA、移动端或桌面端的具体形态。
- 账户体系和多设备同步方案。
- 新用户引导的具体步骤。
- 通知节奏与提醒方式。
- 数据存储位置、保留周期、导出和删除机制。
- 健康数据的授权与隐私边界。
- 详细状态机与异常状态。
- 性能指标和容量上限的具体 SLA。
- 首批外部日历与数据接口。

未决不等于没有要求。实现前必须补齐相应决策并及时更新本 PRD。

## 11. 验收标准

### 11.1 产品行为验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| A01 | 活跃目标数量 | 最多 10 个活跃目标；暂停、完成、归档不计入 |
| A02 | 任务归属 | 所有进入今日待办的任务都关联活跃目标或项目 |
| A03 | 权威状态 | 页面状态由知识图谱和规则计算，不依赖聊天记录 |
| A04 | AI 写入 | 高影响变更未经用户确认不能写入 |
| A05 | 计划稳定性 | 无触发条件时，重复打开页面得到相同计划 |
| A06 | 单一计划 | 每日只生成一份推荐安排，不默认给多套方案 |
| A07 | 临时任务调整 | 新任务进入后只调整必要内容，并显示变化原因 |
| A08 | 完成与进展分离 | 仅完成动作不会自动提高能力或目标进展 |
| A09 | 进度可信度 | 模糊进度显示证据来源、数量、时间和置信状态 |
| A10 | 历史日历 | 只读展示实际活动与证据，不能用于规划 |
| A11 | 可视化 | 图表由规则或查询生成，相同数据得到相同结果 |
| A12 | 关系可信度 | AI 推断关系有来源、置信度和候选状态 |
| A13 | 标准版本 | 标准调整不追溯重算旧进度 |
| A14 | UI 层级 | 目标组合、单目标、行动详情三层结构稳定 |
| A15 | Agent 上下文 | 页面明确显示当前讨论对象，不创建多个独立助手 |

### 11.2 端到端验收场景

使用三个活跃目标：

1. 英语课程。
2. 长期健身。
3. 一个项目型目标。

必须完整跑通：

- 创建目标。
- 输入教师新作业。
- 识别目标和容量影响。
- 生成单一调整计划。
- 完成目标相关任务。
- 记录不同等级的证据。
- 更新模糊进度和证据置信状态。
- 查看不同项目类型的差异化视图。
- 在历史日历中复盘。
- 生成一次周复盘和一个调整实验。

## 12. 验证指标

MVP 不以使用时长、生成字数或任务数量作为主要成功指标。

### 12.1 输入与理解

- 教师通知和任务提取的正确率。
- 用户对提取字段的修正率。
- AI 提出的目标与关系被确认或否定的比例。

### 12.2 计划与控制

- 推荐计划的接受率。
- 临时任务触发调整后的实际完成率。
- 相同输入产生相同计划的稳定性。
- 用户手动撤销或重排计划的频率。

### 12.3 证据与进度

- 目标相关任务附带证据的比例。
- 记录一次证据所需时间。
- 进度变化是否可追溯到证据。
- 用户是否理解“执行完成”与“能力进展”的区别。

### 12.4 长期价值假设

- 四周后仍在维护至少一个长期目标的比例。
- 周复盘完成率。
- 用户是否认为系统帮助其发现了无效投入或识别了真实进展。
- 用户是否愿意在下一次出现新任务时继续使用系统。

具体数值阈值待用户测试后补充。

## 13. 非功能与系统约束

### 13.1 稳定性

- 关键状态不能在聊天上下文中单独维护。
- 图谱写入必须通过结构化校验。
- 计划、进度和图表必须可重复计算。
- 规则和评价标准必须版本化。

### 13.2 可解释性

- 建议必须能够追溯到目标、证据、关系或规则。
- 事实、推断和建议要分开呈现。
- 进度模糊时同时说明证据不足的原因。

### 13.3 可控制性

- 用户能够查看并纠正 AI 提取的对象。
- 用户能够确认、拒绝或修改重大变更。
- 用户可以手动编辑目标、任务、证据与关系。
- 原始知识图谱编辑器只作为高级功能。

### 13.4 数据边界

- 普通外部日历不进入目标统计。
- 与目标无关的事项目标不作为核心数据。
- 医疗、康复、营养等高风险建议必须明确边界。

## 14. 设计决策记录

| 决策 | 结论 |
|---|---|
| 产品类别 | 长期目标进程管理，不是 AI 日历或课程平台 |
| 核心状态 | 个人执行知识图谱 |
| AI 角色 | 单一上下文 Agent，负责感知与解释，不控制权威状态 |
| 领域扩展 | 通用目标模型 + 学习、健身、项目深度模板 |
| 活跃目标 | 最多 10 个 |
| 规划形式 | 目标相关待办，不以日历规划 |
| 历史日历 | 只读复盘，展示实际活动和证据 |
| 计划输出 | 一份推荐安排，不默认给多套备选 |
| 重排时机 | 新承诺、约束变化、不可执行或重大偏差 |
| 可视化 | 项目类型给默认视图，用户可切换合法视图 |
| 模糊进度 | 允许区间和离散状态，必须显示证据与置信状态 |
| 评价标准 | 多层多源，不局限于老师评分 |
| 完成与进展 | 必须分离 |
| UI 层级 | 目标组合 → 单目标 → 行动/证据详情 |
| 协作 | MVP 仅单用户 |
| 平台、通知、隐私 | 未决，由后续技术和合规评估 |

## 15. 团队下一步需要对齐的事项

1. 产品、设计和开发是否接受“待办规划 + 历史日历复盘”的界面组合。
2. 技术团队是否接受“知识图谱为权威状态、规则/查询计算、LLM 只做候选与解释”的控制架构。
3. 数据模型是否从目标、项目、承诺、任务、里程碑、证据、约束、关系、干预和复盘十类实体起步。
4. 是否优先完成英语课程、健身和项目型目标的三个端到端场景。
5. 平台、账户、通知和隐私由哪个角色在下一版 PRD 前补齐。
6. 哪些功能进入原型验证，哪些仅做技术探索，不进入本轮开发范围。
